# Soichiro Yoshimura — AI Profile

公開サイト: https://www.soichiroyoshimura.com

AIの利用状況と、仕事・文章・コーチング・写真・家族をまとめたプロフィールです。Next.js 15 App Routerを使っています。

## 開発と検証

開発環境はNode.js 24.15以降の24系、または22.22.2以降の22系を使います。チャットのDOMテストで使うjsdomの要件に合わせています。

```bash
npm ci
npm run dev
npm run type-check
npm run lint
npm test
npm run build
npm run start
```

## 2つのデザイン

- `/` はAIプロフィール。`?design=telemetry`、`?design=personal-os` も同じ画面です。
- `?design=legacy`、`?design=classic` は旧デザインです。利用データもRSSも取得しません。
- `?view=telemetry`、`?view=legacy` も使えます。両方ある場合は `design`、同じキーが複数ある場合は先頭を優先します。
- `BIO_DESIGN_VARIANT=legacy` で既定表示を旧デザインにできます。環境変数の変更には再デプロイが必要です。

## 利用データ

[ai-usage](https://github.com/soichiyo/ai-usage) が作る `weekly.json` だけを、サーバーからGitHub Contents API経由で取得します。日曜始まり・Asia/Tokyoで全ツールを合算した値です。日別・ツール別のトークン数、生ログ、会話、プロジェクト名、認証情報はブラウザへ渡しません。

### 読み取り用の鍵と公開範囲

- 環境変数: `AI_USAGE_TOKEN`。VercelのProductionとPreviewへ登録済み。
- 鍵の期限: **期限なし**。
- 用途: `soichiyo/ai-usage` のContentsを読むだけ。値をコード・ログ・エラー・PRへ書かず、ブラウザからも使いません。
- 鍵がない環境ではAuthorizationなしで取得を試みます。非公開化後や回数制限で取得できなければ、検証済みキャッシュ、なければ週別の控えを使います。
- ai-usageは2026-11-18に非公開化しました。旧raw URLは匿名アクセスで404です。bioは認証付きで週別の値を読みます。

鍵が失効・権限変更等で使えなくなった場合も、取得失敗として扱います。鍵や応答本文をエラーに含めません。設定変更時には適用先を確認して再デプロイし、画面の更新日と、サーバー側の取得結果（`origin`）を確認します。

### 取得・キャッシュ・控え

`lib/usage/load.ts` は取得・解析・検証に成功した週別データをNext.jsのData Cacheへ保存します。キャッシュのキーは `bio-usage-weekly-v1`、再検証の間隔は1時間、取得のタイムアウトは5秒です。アクセスに応じて再検証されるため、定時取得や必ず1時間以内の反映を保証しません。再検証を始めたリクエストには前の値を返し、その後のリクエストで新しい値を表示します。データ更新だけなら再ビルドは不要です。

再検証に失敗した場合は以前の検証済みキャッシュを保持します。キャッシュがない場合は `content/usage-fallback.json` の週別の控えを表示します。控えも不正なら数値は「—」となり、プロフィールと連絡先は利用できます。モジュール変数だけに前回値を保存しません。

画面には `generatedAt` のJSTの日付だけを `Updated 11/17` の形で表示します。今週分は途中の値です。控えの使用や集計遅延の但し書きは画面に出しません。どちらかのMacが36時間以上更新されていない、または必要なcollectorがない場合はCurrent streakを「—」にします。データの最後の週が先週より古い場合も、連続を0と決めず「—」にします。

出典は `weekly.json` の `tools`（対象ツール）、`coverage.from` / `coverage.to`（取得期間の週）、`collectors[].machine` / `collectedAt`（手元Mac・M1の最終集計日時）で確認できます。現在の対象はClaude CodeとCodexです。クラウド実行分の網羅性は未確認です。取得結果の `origin` が `bundled` なら保存データ、`remote-cache` なら取得済みキャッシュです。

### 控えの更新

1. ai-usageの `weekly.json` を一時ファイルへ取得する。非公開化後は、権限を持つGitHub CLIなどで取得する。鍵の値を表示・保存するための操作は不要。
2. `lib/usage/schema.ts` の `parseUsage` で検証する。未知のキー、欠けた週、日曜でない週、日別の形式は受け入れない。
3. 検証済みの内容を `content/usage-fallback.json` へ保存する。`generatedAt` は書き換えない。
4. `npm test -- lib/usage/schema.test.ts lib/usage/load.test.ts` を実行し、差分を確認してPRにする。合成データで控えを置き換えない。

### 数字の意味

- Total tokensは取得した全履歴の週別合計、Peak weekはその最大週。Peak weekの年月は画面に表示しません。入力・出力・キャッシュを含みます。
- Longest runは、同じ指示の記録間に30分を超える空白がない最大経過時間です。待ち時間を完全に除いた処理時間ではありません。データ側でactiveだけを出します。画面は秒を切り捨て、`13h06m`・`45m` の形にします。数字と小さい単位を横に並べます。正確な秒数・ツール名・発生した週は `longestRun.seconds` / `tool` / `week` に残します。
- 連続は1トークン以上使った週が続いた数。今週が1以上なら今週、0または未取得なら先週から数えます。最長連続も全履歴が対象です。両方とも数字の右横に `weeks` を表示します。
- 図と表は直近26週、日曜始まり。丸1個は5億トークンで端数を切り上げ、0なら丸なし。8段を基本に、必要なら9段以上へ伸ばします。今週は薄い色にします。凡例は「● = 5億 tokens」だけにし、週別の表は読み上げ用に残します。
- データの取得期間内では、日別の記録がない分と未記録のツールを0として合算します。週そのものが取得期間外なら「未取得」で、0とは区別します。
- Skills triedとCustom skillsは `content/skill-tools.ts` の手入力値です。Skills triedは本人指定の265件。Custom skillsは本人作成分から他者の配布物と重複コピーを除いた数で、公開するのは合計だけです。集計元の名前や内訳はリポジトリに保存しません。基準日・出典は画面に出しません。利用データの `snapshots` は従来の形式で読み込めますが、この2つの表示には使いません。

2026-11-18、このMacの収集push、Actionsによる週別更新、本番の今週の値431,490,910 tokensとの一致、Updated 11/18を確認しました。利用データのキャッシュだけを再検証して確認しています。M1側の非公開化後の収集pushは未確認です。次の定時収集後に `collectors` の `m1.collectedAt` とActionsを確認します。経過は[夜間作業報告](docs/superpowers/research/2026-11-18-overnight-report.md)に記載しています。

## Writingの自動更新

新ページは[ZennのRSS](https://zenn.dev/soichiyo/feed)と[noteのRSS](https://note.com/soichiro/rss)をサーバーで取得し、公開日時の新しい順に最大6件を表示します。媒体ごとの枠や固定記事は設けません。URLで重複を除き、未来の公開日時の記事はその時刻まで表示しません。本文・要約・画像は使わず、題名・リンク・公開日時だけを扱います。

`lib/writing/load.ts` は媒体ごとに成功値を6時間キャッシュします。アクセス時に再検証するため、定時更新や6時間以内の反映を保証しません。再検証を始めたリクエストには以前の値を返し、その後に新しい値が見えるようになります。記事更新だけなら再ビルドは不要です。取得は本文の読了まで5秒、最大1MiBで制限します。

片方の取得に失敗しても、もう片方は独立して更新します。再検証失敗時は前回の成功値を保持し、成功キャッシュがない媒体だけ `content/writing.ts` の控えを使います。控えも不正なら取得不能として示します。正常な空フィードは0件として扱い、控えから記事を復活させません。

公開年月はJSTです。公開日時と取得確認日時は別の値です。媒体ごとの `fetchedAt` は実際に取得した日時で、キャッシュを読んだ時刻では上書きしません。`origin` に取得元、`rejectedItems` に読み込めなかった記事数を保持します。「記事の取得状況」と、保存記事・一部取得失敗・取得遅延の注記は画面に出しません。従来の遅延目安は成功取得から24時間以上で、記事の公開日が古いこととは別です。アクセス時の再検証なので、最新の公開記事がまだ反映されていない場合があります。

既存の3記事は旧デザインと控えに残します。旧デザインの題名・年月・順序は変えません。控えの年月しか分からない記事に、架空の公開日や時刻は付けません。正常なRSSに控えを常時追加しないため、新着6件から外れる記事もあります。各媒体へのMoreリンクは残ります。

記事を非公開化しても、成功キャッシュが再検証されるまでは表示に残る場合があります。取得失敗が続けば前回値が残ります。静的な控えと旧デザインからの削除は手動です。

### 記事の控えを手動で更新する

1. `content/writing.ts` の題名・本人の記事URL・媒体・公開年月（`YYYY-MM`）を確認して編集する。旧デザインにも同じ変更が反映されます。
2. `WritingType` とexportを維持する。日時が不明な記事を1日や0時で補わない。
3. `npm test -- content lib/writing/select.test.ts` を実行する。コンテンツのスナップショット差分は、意図した記事変更だけか確認して更新する。
4. 旧デザインと控え使用時の表示を確認し、PR・本番公開へ進める。正常なRSSの表示内容はこの編集では変わりません。

## コンテンツと公開

公開本文は `content/` にあります。Writingの新着はRSS、旧デザインと控えは手動更新です。

### Stack・Connectors・Skillsとロゴ

`stack.ts` の役割別配列、または `connectors.ts` に `{ name, logo?, hidden? }` を追加します。公開してよい名前だけを記入します。全ツールがhiddenの役割見出しは表示しません。

ロゴを省略すれば文字だけで表示します。指定する場合は `logos.ts` の登録キーを使います。空文字・未知キー・継承されたプロパティ名は登録ミスとして検査で落とします。`logoByName` はWriting・Contactだけの対応も含め全件を検査します。採用基準は[素材台帳](docs/assets/logos.md)に従います。2026-11-18の本人の判断で、Stack・Connectorsには公式ロゴ・アプリアイコンをそのまま使います。公式ブランド配布を優先し、公式サイト・公式リポジトリのSVG、次にPNGを使います。第三者のアイコン集は使いません。画像を `public/assets/logos/` へ置き、[素材台帳](docs/assets/logos.md)に出所・条件・確認日・余白・最小サイズを記録します。SVGとPNGに対応し、全登録素材の明暗両方のファイルの実在・大小文字・形式を検査します。暗い背景用の公式素材があれば `darkSrc` へ登録します。`logoByName` は公開名の対応表で、ConnectorsやContactなどで共有します。ロゴを登録しない項目も名前を表示します。画像の形・色・比率は変更しません。暗い背景で見えにくい単色素材は、公式の明暗素材か中立色のタイルを使います。

Stackの `addedAt` は実際に追加した日が分かる場合だけ `YYYY-MM-DD` で記入します。Latestは、本人申告の2026-11-16より新しく、JSTの今日以下で最も新しい表示対象を選びます。同日は配列順を優先し、hidden・日付なし・未来日は候補にしません。候補がなければ「Gemini 4.0」を表示します。この基準は2026-11-16の本人申告です。Latestには名前だけを出し、選定に使う日付・出典はデータに残します。既存ツールの追加日を推測で埋めません。

Stackへの追記例（名前・日付は、実際の公開対象に置き換えます）:

```ts
{ name: "Example tool", addedAt: "2026-11-18" }
```

`stack.ts` の該当する役割の `tools` へ1件追加します。`logo` と `hidden` は任意です。Connectorsも同じ項目形式です。`npm test -- content lib/stack components/sections/ContentDefaults.test.ts` と型検査を実行します。テストは内容を固定せず、追加した項目の形式と表示規則を検査するため、正しい追加に合わせて期待値を書き換える必要はありません。

Stackにツール名を追加しても利用データの対象は増えません。集計対象の追加にはai-usage側の収集・週別合算と、bio側のスキーマ検証の対応が別途必要です。日別やツール別の画面表示は追加しません。

Skillsの掲載名は `content/skill-tools.ts` の `skillTools` へ追加します。Skillsは文字だけで統一し、ロゴを登録しません。Pstackは [cursor/pluginsのpstack](https://github.com/cursor/plugins/tree/main/pstack) を指します。`skillCounts` の数値も同じファイルで更新します。自作スキルの棚卸しでは他者の配布物・同一スキルのコピー・旧名の互換入口を除き、数字だけを転記します。集計元のスキル名・会社名・リポジトリ名・一覧は画面にもコミットにも含めません。ai-usageのスキーマ変更は不要です。

`npm test -- content components/sections/ConnectorsSection.test.ts` と型検査を実行し、390px・1280pxの明暗両テーマで、ロゴと名前、Skillsの文字表示、数字を確認します。旧デザインも確認しますが、その掲載内容は別の配列で維持します。GitHubはContact用の素材を残しています。

### Showcase

`showcase.ts` の `showcaseEnabled` はfalse、公開用配列は空で始めています。掲載時はtrueにして、`title`・`description`・HTTPSの `url`・使用ツールの `tools: ToolEntry[]` を追加します。作品は配列順で並びます。全体がfalse、または個別hiddenを除いた項目が0なら、本体とナビの両方を隠します。

画像は任意です。指定するときは `image: "/assets/showcase/<slug>.jpg"` とし、実ファイルを置きます。画像なしは文字カードになります。`npm test -- content components/sections/ShowcaseSection.test.ts` で必須項目、作品URL・ツール名の重複、未登録ロゴ、画像の存在・大小文字、認証情報を含まないHTTPS URLを検査します。公開用配列へ合成作品を残しません。

作品の題名・説明・URL・使用ツールは本人が選びます。選定後の形の例です（この例自体は公開配列へ追加しません）:

```ts
{
  title: "選定した作品名",
  description: "公開する説明",
  url: "https://example.com/work",
  tools: [{ name: "使用したツール" }],
}
```

本人が内容を選んだ後に `showcase` へ追加し、`showcaseEnabled` をtrueにします。画像は任意です。全体off・空・全件hiddenではナビと本文が両方隠れ、表示できる1件があれば両方出ます。画像付きの場合も390px・1280px、明暗両テーマで確認します。

### Careerの補足
