# 計画6: コンテンツ追加の検証と残るロゴを仕上げる

Date: 2026-11-17

このPRは[再照合結果](../research/2026-11-17-plan6-gap-audit.md)と実装計画を追加する。今回の作業は文書作成まで。以下のTaskは、実装の依頼を受けてから進める。

## 目的

正しい作品・ツール・ロゴを追加したときに、表示とCIの両方が通るようにする。現在の公開内容を維持しながら、確認できる公式素材を採用し、設計書と追加手順を実装に揃える。

正本は[設計書](../specs/2026-11-16-ai-profile-redesign-design.md)。計画5の全体をやり直さず、今回再現した追加時の問題と残る素材に絞る。Cursorの実データ、新しい作品・実績・統計を推測で補わない。

## 作業先・権限・依存

- 作業先はbio。基点は[計画5を含むmain](https://github.com/soichiyo/bio/commit/38072f27e8db1e7fed9a13e3a37e44620a3fb8a7)。開始時に最新main、未コミット変更、ホスト設定を確認する。現在はローカル例外。
- このrepoの担当が直接実装・検証する。作業ブランチは `codex/*`、原則1本の日本語PR。コミットとPRにAI署名を入れない。
- 対象はコンテンツの形式・検証・ロゴ・必要最小限の表示調整と文書。CMS、UIフレームワーク、依存の一括更新は追加しない。
- 利用データの集計・取得、RSSの取得・控え・並び順、チャットのAPI・認証・モデルは変更しない。ai-usage、launchd、秘密、課金も対象外。
- 旧デザインの本文・記事3件・順序・画像・レイアウトを維持する。新しいロゴは新ページにだけ適用する。
- Showcaseは実装後も公開スイッチfalse・配列空。既存Stackの追加日は埋めず、Latestの初期申告を維持する。検証用作品・ツール・ブランドの組合せを公開しない。
- Task 1から順にExpectedを確認する。Task 3の個別素材不足は、その項目だけを保留し、合成入力でTask 4へ進む。入力待ちを理由に独立した作業を止めない。
- 本番公開は実装・デプロイまで依頼された場合だけ行う。取り消し先を確認し、現在のRisk Tiersに従う。この計画PRの作成だけではマージ・公開しない。

## Task 1: 正しいコンテンツ追加を通せるテストとデータ形式にする

**Files:** Modify `content/ai-profile.test.ts`, `components/sections/ShowcaseSection.test.ts`, `lib/stack/latest.test.ts`, `content/stack.ts`。必要な場合だけ `components/sections/StackSection.tsx`, `components/sections/ShowcaseSection.tsx`, `components/AIProfileHeader.tsx`。

1. 一時コピーで、Showcaseの全体スイッチをtrueにして有効な1件を追加した場合と、Stackへ有効な追加日付き1件を追加した場合の失敗を再現する。公開用ファイルの変更をそのまま残さない。
2. Showcaseの「常に空・false」、Latestの「実データでも常にGemini」を固定する期待値を、表示規則を検証する合成入力へ置き換える。全体off、on+空、on+全件hidden、on+1件、画像なし、日付なし・未来・hidden・同率・不正日付の検証を維持する。
3. 実際の公開配列については、必須項目・日付・重複・URL・使用ツール・画像の実在と大小文字を検査する。固定内容の期待値を外すことを理由に、公開データの検証まで削除しない。
4. `stack.ts` を型付きの項目配列へ揃え、`{ name, logo?, hidden?, addedAt? }` を1件足せる形にする。既存名・順序・ロゴ・初期申告は維持する。既存項目へ架空の日付を足さない。
5. propsの差し替えだけでなく、公開モジュールを読む既定経路も検証する。テスト内のモジュール差し替え等で「有効な1件」を渡し、Showcaseのナビと本文が同時に出ること、StackのLatestが変わることを確認する。テストの後に差し替えを解除する。

**Run:** `npm test -- content lib/stack components/sections/ShowcaseSection.test.ts`、`TZ=UTC npm test -- lib/stack`、`TZ=Asia/Tokyo npm test -- lib/stack`、`npm run type-check`。さらに一時コピーで、手順1の有効な追記をしたまま同じ対象テストを実行する。

**Expected:** 有効な追記でテストの期待値を書き換えずに成功する。不正な日付・URL・ロゴ・画像は引き続き失敗する。通常の公開内容ではShowcase非表示、LatestはGemini 4.0と本人申告日のまま。初期状態を維持することと、将来の変更を禁止することを分けられている。

## Task 2: ロゴの名前対応と素材の検証を揃える

**Files:** Modify `content/logos.ts`, `content/ai-profile.test.ts`。必要に応じてModify `lib/content/assets.ts`, `components/ui/LogoTile.test.ts`、Create `lib/content/logos.test.ts`。

1. 実データの `logoByName` の全項目が登録済みキーへ解決する検査を追加する。Stack・Pluginsで使われないWriting専用、Contact専用の対応も対象にする。
2. 対応の省略は有効な文字表示とする。一方、明示した空キー・未知キー・継承プロパティ名は登録ミスとして失敗させる。LogoTileの実行時の文字表示への復帰は維持する。
3. 全登録素材の `src` と任意の `darkSrc` を、実在・パスの大小文字・許可する素材形式で検証する。既存のSVG検査を保ち、PNG等を採用する場合はSVGの文字検査をバイナリへ適用しない。HTML等の誤取得は採用しない。
4. Zennだけ、Contactの名前だけに未知キーを割り当てた例、暗色用ファイル欠損、ファイル名と途中ディレクトリの大小文字違いを否定例にする。有効な登録と対応省略も確認する。
5. ファイル読み取りの検査はテスト側へ置き、ブラウザの部品へNode.jsのファイル操作を持ち込まない。登録データを複数箇所へ複製しない。

**Run:** `npm test -- content lib/content components/ui/LogoTile.test.ts`、`npm run type-check && npm run lint`。一時コピーで `logoByName` に `Zenn: "missing-logo"` を加え、実データ検査の失敗も確認する。

**Expected:** 未登録の名前は文字で使え、登録した誤対応はCIで検出する。新しい対応がどのセクションだけで使われるかに検査が依存しない。実ファイル・テーマ違いの不備も検出する。

## Task 3: 残る公式素材を確認して採用する

**Files:** Modify `content/logos.ts`, `docs/assets/logos.md`。Add 確認済みの `public/assets/logos/*`。個別項目への対応付けが必要な場合だけModify `content/stack.ts`, `content/plugins.ts`。

1. 素材台帳の未確認項目を読み、公開名と製品を同定できるものから確認する。WritingのZenn/noteを先に調べ、次にStack・Plugins・Contactを進める。
2. 公式配布ページ・ファイル・利用条件を確認する。403は別の公式配布経路やブラウザでの確認を試せるが、認証の回避や第三者のロゴ集への置換はしない。素材が得られない項目を繰り返し取得し続けない。
3. 出所・利用条件の参照・確認日・保存パス・テーマ別の扱い・最小サイズや余白を台帳へ記す。製品名とロゴの対応が不明なMuse Code等は、親会社や別製品のロゴを仮置きしない。
4. 条件を満たす素材だけをローカルへ保存し、共通の登録へ追加する。既存の3ブランドの条件も維持する。色反転や形状の加工でテーマへ合わせない。
5. 残る項目は、取得不能・条件未確認・製品同定待ちを区別し、何が確認できれば再開できるかを台帳に残す。文字表示は継続する。

**Run:** Task 2の対象テスト、`npm run type-check && npm run lint`。両テーマの表示はTask 4でまとめて確認する。

**Expected:** 採用した素材と文字のままの項目を明確に分けられる。全未確認項目に確認結果または必要な入力が残る。確認できた素材は登録済みで、取得できなかった素材を「対応済み」としない。追加可能な素材が0件でも、理由が記録されていればTask 4へ進める。

## 停止条件と再開条件

| 条件 | 止める範囲 | 担当・再開条件 |
|---|---|---|
| 公式素材の条件・製品との対応が不明 | 該当ロゴの採用のみ | 実装担当が公式情報を確認。製品の同定ができない場合だけ本人に確認 |
| 有効な追記でもCIが落ちる、不正データを通す | 該当Taskを未完了とし、公開を止める | 実装担当が再現例と検査を修正して再実行 |
| 旧画面、利用データ、RSSの契約が変わる | その変更の公開 | 実装担当が範囲を戻すか、変更が必要な根拠と新しい範囲を確認 |
| 作品・実績・統計の公開内容が未選定 | 公開データへの追加のみ | 本人の公開可能な文章・根拠・値を待つ。仕組みの検証は進める |
| Cursorの実CSVがない | データ取り込みの設計・実装 | 本人が対象期間の実CSVを用意し、データ側担当がローカルで確認。今回のbio作業は進める |
| 新しい認証・課金・非公開データ送信が必要 | 該当操作 | 対象を限定した明示承認を得る。計画6へ黙って追加しない |
