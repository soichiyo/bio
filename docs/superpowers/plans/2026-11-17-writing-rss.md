# 計画4: WritingをRSSで自動更新する

Date: 2026-11-17

このPRは実装計画だけを追加する。アプリの変更、依存パッケージの導入、マージ、本番公開は、実装の依頼を受けてから行う。

## 目的と方針

新しいAIプロフィールのWritingを、Zennとnoteの公開RSSから更新する。記事を公開した後にbioの手動編集や再ビルドを必要としない。現在の行形式、媒体名、題名、年月、媒体の一覧へのリンクは保つ。

設計の正本: [AIプロフィールの設計書](../specs/2026-11-16-ai-profile-redesign-design.md) の「文章の自動更新」。計画3で決めた、新ページを通常表示にして旧デザインを残す方針を継承する。

この計画では次を採用する。表示件数や固定記事は、過去に本人が指定した決定ではなく、今回の計画で置く初期方針。

- 新ページは2媒体を合わせて公開日時の新しい順に最大6件。媒体ごとの枠は設けない。
- 既存の3記事は削除せず、旧デザインの表示とRSS取得失敗時の控えとして残す。正常なRSSに既存記事を常時足したり、先頭へ固定したりしない。
- 旧デザインの本文・記事順・見た目を維持し、RSSも利用データも取得しない。
- RSSは媒体ごとに独立して6時間キャッシュする。アクセスに応じた再検証で、定時実行は作らない。

## 現状と事前確認

手元のbioはホスト設定上のローカル例外。2026-11-17に `main` と `origin/main` の一致、未コミット変更がないことを確認した。基点は[計画3の公開時点](https://github.com/soichiyo/bio/commit/b443a2a747fa8b721c4257ce73bd7132ec6f3423)。実装開始時には改めて最新mainを確認する。

- `content/writing.ts` は `WritingType[]` の3件。日付は `YYYY-MM` で、公開時刻は持たない。
- 新ページは `components/pages/AIProfilePage.tsx` 内でこの配列を直接描画している。
- 旧デザインは `components/sections/WritingsSection.tsx` が同じ配列を使う。`content/index.ts` の公開exportとコンテンツのスナップショットテストがある。
- `app/page.tsx` はデザインを決め、新ページだけ `getUsage()` を呼ぶ。
- Next.js 15.5.14、Vitest、`server-only` が導入済み。RSS/XMLパーサは直接依存にない。

以下は同日のHTTP取得で確認した事実。件数や先頭記事は将来変わるため、本番CIの固定期待値にはしない。

| 媒体 | RSS | 応答と構造 | 取得時の件数 | 最新記事の公開日時（JST） |
|---|---|---|---:|---|
| Zenn | https://zenn.dev/soichiyo/feed | 200、text/xml、RSS 2.0のchannel/item | 6 | 2026-08-21 16:42:32 |
| note | https://note.com/soichiro/rss | 200、application/xml、RSS 2.0のchannel/item | 20 | 2024-07-16 20:52:16 |

両方に `title`、`link`、`guid`、`pubDate`、`description` がある。Zennの日時はGMT、noteは `+0900`。`channel.link` はそれぞれ本人のプロフィールURLと一致し、取得URLのリダイレクトはなかった。画像や著者の追加フィールドもあるが、今回の表示には使わない。

既存記事のURL3件は全てRSSにも存在した。GTDの記事はRSSと手入力でハイフン等の題名表記が異なる。同じURLなら別記事にせず、新ページの正常取得時はRSSの題名を使う。旧デザインの題名は変更しない。

現在の新着6件はすべてZennになる。noteの既存記事は新ページの6件から外れるが、More on noteと旧デザインから読める。記事の削除ではなく、新着順による表示対象の変更である。

## 既存記事と2つのデザイン

| 対象 | 実装後 |
|---|---|
| `/`、telemetry / personal-osの別名 | RSS由来の新着6件を表示 |
| legacy / classic、環境変数で選ばれた旧デザイン | 現在の3記事を同じ順序・題名・年月で表示 |
| `content/writing.ts` の `writings` | 値とexportを維持。旧デザインと媒体別の控えの正本 |
| 正常取得に含まれる既存記事 | RSSの題名・公開日時で扱い、URL単位で1件にする |
| 正常取得に含まれない既存記事 | 新ページへ追加しない。控えから復活させない |
| 取得に失敗し、成功キャッシュもない媒体 | その媒体の既存記事だけを控えとして使う |

`WritingType.date` をISO日時へ変えない。新しいRSS用の型は `lib/writing/types.ts` に分け、既存データを読み込む境界で変換する。控えの年月を表示のために架空の1日や0時へ変換しない。

固定記事の指定は現在ないため、初期状態で固定表示を追加しない。既存3件すべてを固定すると新着が下へ追いやられる。固定機能や媒体別の最低表示枠が必要になった場合は、表示件数と合わせて別途決める。

## 対象と境界

対象は2つの公開RSSの取得・解析・検証・キャッシュ・統合、新ページのWriting表示、旧画面の保持、テストと説明文書。サーバーだけで取得し、ブラウザへXMLや記事本文を渡さない。

記事本文や要約の転載、記事ページの巡回、RSS外の過去記事の収集、ロゴ素材の追加、チャットAPI、利用データの仕様、ai-usage、CMS、データベース、認証情報、Cron、launchd、GitHub Actionsによる定期取得は対象外。RSSを記事アーカイブとして蓄積しない。

実装作業はこの個人repoで行う。通常の作業ブランチ・日本語PRを使い、コミットとPRにAI署名を入れない。この計画PRの作成から、アプリ実装や公開まで許可されたとは解釈しない。

## データと取得の契約

### 入力と正規化

- `sources.ts` に媒体ID、RSS URL、プロフィールURL、記事URLの許可範囲、表示件数6、再検証21,600秒を定義する。URLを検索パラメータや任意入力から受け取らない。
- `parseFeed(xml, source)` はRSS 2.0のchannelを検証し、本人の `channel.link` と一致することを確かめる。HTMLのログイン画面や別人のフィードを記事として採用しない。Atomなど未確認の形式は今回は扱わない。
- 各itemから取得するのは題名・記事URL・公開日時だけ。description、本文、画像、著者画像、独自タグは捨てる。guidは記事リンクの代用品にしない。
- URLはHTTPS、認証情報・任意ポートなし、Zennは `zenn.dev/soichiyo/articles/<slug>`、noteは `note.com/soichiro/n/<id>` に限定する。正規化時に検索パラメータ・fragment・末尾スラッシュを取り除き、URLを同一性のキーにする。他人の記事、プロフィール、短縮URL、javascript等のURLは採用しない。
- 題名は文字列をtrimし、空なら拒否する。数字だけの題名も文字列のまま保つ。CDATA、XML標準実体、数値参照を扱い、二重デコードしない。Reactの文字列として描画し、HTMLとして挿入しない。
- 公開日時は `pubDate` からタイムゾーン付き日時として検証してUTCのISO文字列にする。欠落・不正値を取得時刻や今日へ置き換えない。年月表示はAsia/Tokyo。`lastBuildDate` は記事の公開日時や成功取得時刻として使わない。
- XML不正、channel不正、DTD/ENTITY宣言は媒体全体の失敗。外部・独自実体の展開を行わない。itemの必須値不正はそのitemを除外し、除外件数を保持する。itemがあるのに有効itemが0件なら失敗とする。正常なchannelにitemが0件の場合は「成功した空フィード」とし、控えで記事を復活させない。

XMLは正規表現だけで解析しない。候補は `fast-xml-parser`。計画時にnpm公開情報で5.12.1、MITを確認した。実装開始時に現行の修正状況・Node互換性と公式のパーサ設定を確認して版を固定し、lockfileを更新する。DTD拒否、標準実体、CDATAの挙動は合成入力で確認する。今回、依存パッケージは追加しない。

### 表示用の型と並び順

`WritingEntry` は `title`、正規化済み `url`、`platform`、`publishedAt: string | null`、`displayMonth: YYYY-MM`、`datePrecision: instant | month` を持つ。RSSはinstant、既存の控えはmonthとする。

1. 各媒体の結果を統合し、正規化URLで重複を除く。同じURLでRSSと控えが競合する場合はRSSを優先。同じフィード内の競合は新しい公開日時、同日時なら先のitemを採用する。題名だけで異なるURLを統合しない。
2. RSSの未来の公開日時は、サーバーで渡す `now` より後なら表示候補から外す。この判定は取得キャッシュの外で行い、時刻が来れば再取得なしでも候補に戻る。
3. JSTの年月を降順、同月の日時既知同士は公開日時を降順。同月の年月しかない控えは日時既知の記事の後ろに置き、控え同士は `writings` の元の順を保つ。日時まで同じRSS記事は媒体ID（zenn、note）とURLの昇順で安定させる。
4. 最大6件に切る。媒体ごとの枠、タイトルの類似度判定、表示のための擬似公開日時は使わない。

### キャッシュと部分失敗

`getWriting()` は記事一覧と媒体別の状態を返す。媒体別状態は `origin: remote-cache | bundled | unavailable`、実際に取得・検証を終えた `fetchedAt: string | null`、除外item数。記事の公開日と取得確認日を区別する。取得不能でも例外でページ全体を落とさない。

- 固定URLを `cache: no-store` で取得。5秒タイムアウトは本文の読了まで有効にする。HTTPエラーとリダイレクトは失敗にする。本文はストリームの実読込で最大1MiBに制限し、Content-Lengthだけに依存しない。
- 媒体ごとに独立した `unstable_cache` を用意する。キーとtagにも媒体を含め、6時間後のアクセスで再検証する。2媒体の取得は並列にする。
- 取得→XML解析→検証→成功時刻の付与までをキャッシュ関数内で行う。失敗時は固定コードのErrorをthrowし、本文やパーサの入力断片をログへ出さない。失敗時の控えや空配列を成功キャッシュに保存しない。
- 既存の成功値がある場合、再検証失敗時はNext.jsによる前回値の保持を使う。キャッシュ読み出しで成功値を得られない場合だけ、キャッシュ関数の外で媒体に対応する控えへ切り替える。片方の失敗で他方を控えへ戻さない。
- 控えは検証して使う。対応する控えも不正ならその媒体はunavailable。両方がunavailableまたは正常空フィードなら一覧を空にできるが、媒体一覧へのリンクとプロフィール・連絡先を残す。0件の正常応答と取得不能は文言で分ける。
- アクセスのない間は更新しない。最初の再検証リクエストでは以前の記事が返り、再検証終了後のリクエストで新しい記事になる。6時間以内の反映を保証しない。モジュール変数だけを前回成功値の控えにしない。
- `remote-cache` は今回のネットワーク取得成功を意味しない。表示時刻を取得時刻として書き直さない。古い記事しかないnoteを「取得失敗」と判断しない。

### 画面へのつなぎ方

新ページ専用の `WritingSection.tsx` を作り、現在の行の見た目を移す。旧デザインの複数形 `WritingsSection.tsx` はそのまま残す。新コンポーネントはServer Componentとし、ブラウザからRSSを取得しない。

`app/page.tsx` のデザイン分岐を維持し、新ページでだけ `getUsage()` と `getWriting()` を並列に呼ぶ。`AIProfilePage` へ結果を渡す。RSS結果の取得失敗をusageの結果へ波及させず、両ローダーがそれぞれの控えを解決する。共通CSSを広く変更しない。

通常は記事の行とMoreリンクを表示し、媒体ごとの取得確認日時は「記事の取得状況」の折りたたみに置く。控えを使用するときは「一部の記事は保存分です」または「保存している記事を表示しています」と短く示す。成功取得から24時間以上経過した媒体があれば「記事の取得確認が遅れています」と示す。除外itemがある場合も詳細で分かるようにする。表示候補が0件で、全媒体が正常取得できている場合は「表示できる公開記事はありません」とする。0件で取得不能な媒体があれば「記事を取得できません」とし、正常空の媒体と失敗した媒体を詳細で区別する。古い公開日を遅延の根拠にしない。

3. 実装・公開を依頼された場合は、CIとVercelプレビューを確認し、個人repoのmerge条件とRisk Tiersに従って公開する。切り戻し先の正常な本番デプロイを確認しておく。
4. 本番Readyとソースの版の一致、新ページの記事順とリンク、旧デザインの3記事を確認する。環境差でRSSが取得できず控えになっている場合は、RSS自動更新の本番確認が済んだとはしない。

**Expected:** 検証結果と運用方法がPRと文書に残る。公開を依頼された実装では、利用者が本番で新着記事と旧デザインの両方を使える。

## 完了条件と止める条件

今回の計画作成の完了条件は、この計画書だけの日本語PRが作成されていること。実装後の完了条件は、Task 1〜6のExpected、実データとの一致、本番Readyと新旧画面の確認がそろうこと。

- RSSの本人確認・形式が変わった、または実RSSとの照合が合わない場合は、原因を確認するまで公開を止める。UIや合成テストなど独立した作業は進めてよい。
- キャッシュ再検証失敗で以前の値を失う、正常な空フィードが控えで復活する、旧画面で取得が走る場合は修正してから公開する。
- 認証が必要になった場合は鍵の作成や非公開データの取得へ広げない。公開RSSで継続できるかを確認し、できなければ未確認と報告する。
- 新しい固定記事、記事本文の掲載、他アカウントの追加、旧デザインも自動更新する変更は、この計画に黙って追加しない。
