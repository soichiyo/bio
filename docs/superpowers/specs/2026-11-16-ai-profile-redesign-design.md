# AIプロフィール刷新 + リファクタリング 設計

Date: 2026-11-16

モック（承認済み）: https://claude.ai/artifact/7g8v8JBf8oAYPzMT8BHyWZ

この文書で「決定」と書いたものは本人が会話で決めたこと、「提案」と書いたものは設計側の判断で、まだ本人の確認を受けていない。

## 意図

soichiroyoshimura.com を、転職や新規プロジェクト獲得の営業で使えるページにする。見た人に「AIをここまで使い込んでいる人なら、新しいモデルが出てもすぐこの水準で使うだろう」と思わせたい。同時に、キャリア・コーチング・写真・家族を残して、多角的な人だと伝える。

いまのページは bento 型で情報量はあるが、意味のない数字（Projects / 3、Family / 5）や固定値のグラフが混ざり、同じ内容が上下で2回出ている。これを整理し、実データに置き換える。

## 既存ページの確認（2026-11-17）

現在は旧デザイン（`LegacyBioPage`）と現行デザイン（`TelemetryBioPage`）の2つがある。`?design=legacy`で旧デザイン、`?design=telemetry`で現行デザインを表示する。指定がない場合は現行デザインになり、環境変数`BIO_DESIGN_VARIANT=legacy`を設定した場合だけ旧デザインになる。切り替えは`app/page.tsx`と`lib/design-variant.ts`にある。

基盤整備では両方を残した。2026-11-17に、計画3では現行デザインを新しいAIプロフィールへ置き換え、旧デザインは比較・退避用に残すと決定した。`?design=telemetry`は新ページ、`?design=legacy`は旧デザインを表示する。第3のデザイン名は増やさない。`ProfileHeader`は旧デザインで使用中のため削除しない。

実装計画: `docs/superpowers/plans/2026-11-17-ai-usage-display.md`。

## ゴール

- 冒頭でアイコン・名前・@soichiyo と、AI利用の実績値（累計トークン、最大トークン、最長タスク、最長連続日数、現在の連続日数）を見せる。
- Claude Code・Codex・Cursor をまたいだ1年分の利用状況を、ツール別に色分けした草として見せる。
- Stack と Plugins を本物のロゴで並べる。
- Showcase（AIと一緒に作ったものの棚）を用意する。公開時は非表示にし、載せるものができたら出す。
- Writing を Zenn と note から自動で更新する。
- Stack・Plugins・Showcase の項目を、データを1件足すだけで追加できる。
- 今後の保守がしやすいコードにする。

## 非ゴール

- 案件ごとのトークン集計（案件名が漏れる恐れがあり、自動化もしにくい）。
- プラグイン一覧の自動取得（スキル名に会社名が含まれるため、手で選ぶ）。
- Cursor の自動取得（公式の個人向けAPIがない。月1回の手動取り込みにする）。
- 草の「週別」「累計」表示の切り替え（初版は日別とツール絞り込みだけ）。
- 複数ページ化、CMS導入、言語切り替え。

## やってはいけないこと

- 出どころのない数字やグラフを載せる。すべての数字に出どころと基準日を持たせる。
- 説明文で画面を埋める。見出しの下の説明文は置かない。
- プロジェクト名・ファイルパス・会話内容を外に出す。

- 見た目の言語は今のものを引き継ぐ: 暗い背景が基本でライトも対応、Doto は大きな数字だけ、Space Mono はラベル、Space Grotesk は本文、赤（#D71921）は連絡ボタンだけ。
- 変更は小さな `codex/*` ブランチとPRで進める（AGENTS.md の手順）。

## コンテンツの持ち方（追加しやすさ）

`lib/data.ts`（537行、型と中身が混在）を、種類ごとのファイルに分ける。

```
content/
  types.ts
  profile.ts      名前、@ID、タグライン、SNSリンク
  stack.ts        ツール（名前、ロゴ、色、役割、追加日）と行
  plugins.ts
  showcase.ts
  writing.ts      自動取得に失敗したときの控えと、固定表示したい記事
  career.ts  coaching.ts  expertise.ts  photos.ts  family.ts  life.ts
  logos.ts        ロゴの名前 → 画像の対応表
public/assets/
  showcase/<slug>.jpg
  logos/<key>.svg
```

- **Showcase に足す**: `showcase.ts` に1件書き、画像を `public/assets/showcase/` に置く。並び順は配列の順。`hidden: true` で隠せる。
- **Stack / Plugins に足す**: 配列に1件書く。ロゴは `logos.ts` の名前で指定する。Stack は役割（Agents / Harness など）を書けば、その見出しの下に並ぶ。使わなくなったツールは消すか `hidden: true` にする。
- **Latest の行**: Stack のツールに追加日を持たせ、いちばん新しいものを自動で表示する。新しいツールを足すだけで更新される。
- **ロゴ**: アイコン集のパッケージにあるものはそこから、無いものは各社の公式素材を `public/assets/logos/` に置く。どちらに当たるかは実装時に確認する。
- **足し間違いの検出**: 必須項目の欠け、画像ファイルの不在、ロゴ名の未登録をテストで落とす。

## 利用データの仕組み

2026-11-17 の調査（`docs/superpowers/research/2026-11-17-usage-log-probe.md`）を受けて、この節を書き直した。実装計画は `docs/superpowers/plans/2026-11-17-ai-usage-collector.md`。

```
各 Mac（毎日）                               データ専用リポジトリ soichiyo/ai-usage        サイト
ccusage でログを集計 → 自分の machines/<id>.json を更新 → 全 Mac 分を足して usage.json → 定期的に読み直して表示
```

- 集計のコードもデータ専用リポジトリに置く。各 Mac はこのリポジトリを1つ取得して毎日実行するだけでよく、bio リポジトリの取得や依存の導入は要らない。
- 集計する Mac は、手元の Mac と m1-runner-01 の2台（調査で確認できた範囲）。

### 出どころ

| ツール | 取り方 | 備考 |
|---|---|---|
| Claude Code | ccusage 20.0.51 で集計（自動） | 直近7日で生ログの集計と一致（調査で確認） |
| Codex | ccusage 20.0.51 で集計（自動） | 同上。履歴圧縮時の追加トークンも ccusage の合計に含まれている |
| Cursor | ダッシュボードのCSVを月1回取り込む（手動） | 手元のログのトークン数は不完全で使えない（手元は全件ゼロ） |
| opencode | ccusage で取れるが、初版では集計しない | 対象ツールの一覧に名前を足せば集計される |
| Muse Code / Grok 系 | 対象外 | 手元のログにトークン数の記録を確認できなかった |

### 外に出すもの

データ専用リポジトリに書いてよいのは、下の形にある項目だけ。プロジェクト名・パス・セッションID・モデル別の内訳・会話内容・自由記述は出さない。形を厳密なスキーマとして定義し、そこに無いキーや型の違う値があれば書き出しを止める。自動集計・Cursor の取り込み・手入力のすべてが、同じ検証を通ってから書き出される。

### データの形

Mac ごとのファイル `machines/<id>.json`（その Mac だけが書く）:

```json
{
  "schemaVersion": 1,
  "machine": "air",
  "collectedAt": "2026-11-17T03:07:00+09:00",
  "ccusage": "20.0.51",
  "tools": {
    "claude-code": {
      "coverage": { "from": "2026-07-27", "to": "2026-11-17" },
      "daily": { "2026-11-16": 100962003 },
      "longestRun": { "rawSeconds": 156565, "rawDate": "2026-07-30", "activeSeconds": 0, "activeDate": "2026-07-30" }
    }
  }
}
```

サイトが読む `usage.json`（全 Mac 分を足したもの）:

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-11-17T03:07:00+09:00",
  "collectors": [{ "machine": "air", "collectedAt": "2026-11-17T03:07:00+09:00" }],
  "sources": {
    "claude-code": { "mode": "auto", "coverage": { "from": "2026-07-27", "to": "2026-11-17" } },
    "codex": { "mode": "auto", "coverage": { "from": "2025-09-17", "to": "2026-11-17" } }
  },
  "daily": [
    { "date": "2026-11-16", "tokens": { "claude-code": 100962003, "codex": 80141318 } }
  ],
  "longestRun": { "seconds": 0, "tool": "codex", "date": "2026-06-19", "rule": "active" },
  "snapshots": [
    { "key": "skillsTried", "value": 265, "asOf": "2026-11-16", "source": "chatgpt-profile" }
  ]
}
```

- 上の例の `activeSeconds` と `longestRun.seconds` は、まだ集計していないので 0 にしてある。
- **未取得とゼロの区別**: `coverage` は、そのツールのデータを取得できている期間。`daily` の `tokens` には、その日が `coverage` に入っているツールだけを書く。キーがあって `0` なら「使っていない」、キーが無ければ「未取得」。
- **snapshots**: 自動で取れない数字を手入力する場所。`key` は決めた一覧（`skillsTried` `skillRuns` `topReasoningShare` `fastModeShare`）だけ、`value` は数値、`source` は `chatgpt-profile` か `manual` だけ。
- **トークンの数え方**: ccusage 20.0.51 がツールごとに出す `totalTokens` をそのまま使う。入力・出力・キャッシュの合計で、キャッシュの読み込みが大半を占める。日付の区切りは Asia/Tokyo。版を上げるときは、同じ日の値が変わらないことを確かめる。
- 累計、最大、最長連続、現在の連続は、サイト側で `daily` から計算する。

### 更新の決まり

- 各 Mac は毎回、残っているログ全体を ccusage で集計し直す（加算はしない）。同じ日に何度実行しても結果は同じになる。
- 自分の `machines/<id>.json` の「ツール × 日付」ごとに、保存済みの値と集計し直した値の大きいほうを残す。古いログが消えても、保存済みの値は減らない。
- `usage.json` は、全 Mac のファイルを「ツール × 日付」で足して作る。
- 当日分は途中の値で、翌日以降の実行で確定する。
- 手で直した値は `overrides.json` に書く。間違って大きい値が残ったときもここで直す。
- 優先順位は、手で直した値、取り込んだ値（Cursor）、自動集計の順。

**セッション単位の台帳をやめた理由（設計側の判断）**: 前の版では「ツール × セッション × 日付」の非公開の台帳を持つとしていた。調査の結果、ccusage の出力からはセッション別の日別値が取れず、取るには Claude Code と Codex の生ログを自前で読む処理を持つ必要があるとわかった（Codex は履歴圧縮の追加分の扱いが要る）。ログの形式が変わるたびに直す負担が大きいので、解析は ccusage に任せ、日付単位の最大値にする。この方式で取り逃すのは、同じ日のログが一部消え、かつ同じ日に新しい記録が足された場合だけ。ログが消えるのは保持期間を過ぎた古い日で、新しい記録が足されるのは当日なので、通常は重ならない。

### 連続日数の数え方

- どれかのツールで1トークン以上使った日を「使った日」とする。
- 取得できているツールがすべてゼロで、未取得のツールがある日は、いったん切れた扱いにする。あとから取り込めば計算し直されてつながる。実際より多く見せない側に倒す。
- 今日がまだゼロでも、現在の連続日数は昨日までで数える。
- いちばん早い `coverage` の開始日より前には遡らない。

### 最長タスクの定義（決定: 案1、activeを表示）

セッションの開始から最後の記録までの長さは使わない。放置や中断の時間が混ざるため（レビューで、約661時間・途中に約32時間の空白があるセッションが見つかった）。

決定（2026-11-17）: 1回の指示の開始から完了までの経過時間を、手元のログから自動で取る。画面のラベルは「Longest run」（ラベルは提案）。

取り方: Claude Code は `type = system`・`subtype = turn_duration` の `durationMs`、Codex は `event_msg`・`payload.type = task_complete` の `payload.duration_ms`。ccusage では取れないので、この2つだけは集計スクリプトがログを直接読む。

調査でわかった最大値（保存済みの記録全体）:

| ツール | 手元の Mac | m1-runner-01 |
|---|---|---|
| Claude Code | 43時間29分（2026-07-30） | 6秒 |
| Codex | 15時間30分（2026-06-19） | 41分 |

- Codex の 15時間30分は、ChatGPT プロフィールの「最長タスク」と同じ値。プロフィールも同じ記録を数えているとみられる。
- 前の版に書いた「約85分」「約26分」は、一部のログだけを見た値だった。
- これらの長い値が、Mac のスリープや承認待ちの時間を含むかは未確認。

そのため集計では2つの値を記録する。記録の間に30分を超える空白がある指示を除いた最大値（`active`）と、除かない最大値（`raw`）。

決定（2026-11-17）: 画面には `active` を表示する。初回集計の値はCodexの47,175秒（13時間6分15秒）、2026-09-09。待ち時間を完全に除いた処理時間ではない。`usage.json` にactiveの記録がない場合は、rawへ切り替えず未取得として表示する。

### わかっている限界

- 手元のログに残る分しか数えられない。クラウド側で実行した分が手元のログに現れるかは未確認で、ChatGPT のプロフィールに出ている Codex の数字（累計 502.9億など）より小さく出る可能性がある。
- 遡れる範囲は Mac とツールで違う。Claude Code は手元が 2026-07-27 から、M1 が 2026-10-17 から。Codex は手元が 2026-04-09 から、M1 が 2025-09-17 から。
- 集計を始める前の履歴は、手元に残っているログの範囲までしか遡れない。
- Mac を数日開かなければ更新が止まる。更新日を表示して隠さない。

## 文章の自動更新

- [Zenn](https://zenn.dev/soichiyo/feed) と [note](https://note.com/soichiro/rss) の公開RSSをサーバーで取得し、新ページに公開日時の新しい順で最大6件を表示する。媒体ごとの枠・固定記事は設けない。
- 媒体ごとに6時間キャッシュし、アクセス時に再検証する。再検証中は以前の値を返すため、6時間以内の反映は保証しない。記事更新だけなら再ビルドは不要。
- 取得失敗時はその媒体の前回成功値を保持する。成功キャッシュがない媒体だけ `content/writing.ts` の控えを使い、控えも不正なら取得不能と示す。正常な空フィードは0件にし、控えで記事を復活させない。
- 公開年月はJST、取得確認日時は媒体ごとに別に示す。成功取得から24時間以上経過した場合は知らせる。年月しかない控えに架空の日時を付けない。
- 旧デザインはRSSを取得せず、既存3記事を同じ題名・年月・順序で残す。非公開化した記事も再検証までは残りうる。控えと旧デザインからの削除は手動。
- 入力・失敗時の扱い・検証手順は[計画4](../plans/2026-11-17-writing-rss.md)、控えの更新方法は[README](../../../README.md)に記載。
